# MEF-ADR-0047: Doctrina de servidores MCP serverless

- **Fecha**: 2026-08-30
- **Estado**: aceptado
- **Aplica a**: doctrina general del marco para todo servidor MCP (Model Context Protocol) que un Bounded Context expone -- ruta tecnica de hosting, granularidad del servidor, aislamiento frente al codigo del BC y diseno de las tools. Aplicable a cualquier Bounded Context de cualquier consumidor del marco; el cuerpo normativo no referencia ningun proyecto, archivo ni issue de un consumidor concreto (ver seccion "Alcance", mas abajo). Cross-referencia MEF-ADR-0009 (mensajes `.resx` per-aggregate, que esta doctrina extiende a los mensajes runtime de una tool), MEF-ADR-0013 y MEF-ADR-0022 (smoke tests y autenticacion de CI por OIDC, citados como hermanos cuya extension a MCP -- como se prueba un servidor MCP en CI, con que credencial -- queda fuera de este ADR) y MEF-ADR-0039 (composicion canonica de ensamblados por rol: el aislamiento del servidor MCP frente al BC es un caso mas del mismo principio -- la verdad viaja en el contrato, no en un tipo compartido). Ver mas abajo la lista precisa de issues bloqueados.

**Issues bloqueados por este ADR**: #767 (ADR de testing/CI de servidores MCP), #768 (`/scaffold-mcp` fase 1) y #771 (doctrina del `planner` publicado para reconocer la senal de este patron) -- los tres referencian este ADR como su fundamento normativo. #769 y #770 (`/scaffold-mcp` fases 2-3) dependen de #768, no directamente de este ADR.

## Contexto

Un Bounded Context del marco necesita, cada vez con mas frecuencia, exponer su funcionalidad a un asistente conversacional (Claude, GitHub Copilot u otro cliente MCP) para que ese asistente pueda consultar datos de negocio o ejecutar comandos en nombre de un usuario humano, sin que el humano tenga que aprender la superficie HTTP cruda del BC. El **Model Context Protocol** (MCP, `https://modelcontextprotocol.io`) es el estandar abierto que resuelve exactamente ese problema: *"a client-server protocol designed to help language models and agents more efficiently discover and use external data sources and tools"* [1], en el que *"servers [...] expose tools that can be invoked by language models"* (Model Context Protocol, especificacion 2025-06-18, "Server Features: Tools" [6]).

Antes de este ADR el marco no tenia ninguna doctrina escrita sobre como un BC debia construir, hospedar y disenar ese servidor. Sin ella, cada consumidor habria resuelto MCP a su manera -- que runtime de hosting, cuantos servidores por BC, si el servidor puede referenciar el codigo del dominio directamente, como disenar las tools para que un agente las use bien --, exactamente el mismo riesgo de reinvencion reactiva y divergencia entre consumidores que MEF-ADR-0039 ya evito para la composicion de ensamblados de evento: cada greenfield futuro que adoptara MCP habria pagado el costo de descubrir estas mismas decisiones desde cero, o peor, habria heredado un acoplamiento que despues hay que deshacer bajo presion.

### Alcance

Este ADR fija **doctrina general del marco**, aplicable a cualquier Bounded Context de cualquier consumidor: el cuerpo normativo (seccion "Decision") usa vocabulario neutro (`<RootNamespace>.Mcp.{Proposito}`, "el BC", "el consumidor") y no nombra ningun proyecto, archivo ni issue de un consumidor concreto.

La doctrina no es especulativa -- se valido empiricamente en un piloto completo sobre un consumidor real, mergeado y con su suite de smoke tests verde contra un entorno desplegado, antes de escribirse --, pero esa evidencia (que consumidor, que issues y PRs, que resultado de smoke) queda registrada en el issue #761 de este repo (seccion "Origen" y su comentario con la doctrina de testing/CI), deliberadamente **fuera** de este ADR: una doctrina general del marco no se ata a la trazabilidad de un consumidor particular, que envejece y deja de ser verificable para quien lee el ADR desde otro proyecto.

### Que queda fuera de este ADR

- **Como probar un servidor MCP y con que credencial en CI** (la extension de MEF-ADR-0013 y MEF-ADR-0022 a este dominio): issue #767, que este ADR bloquea.
- **El agente scaffolder que materializa esta doctrina en codigo** (`/scaffold-mcp`, sus fases 1-3): issues #768/#769/#770.
- **Como el `planner` reconoce, durante el refinamiento de un issue, la senal de que un BC necesita un servidor MCP**: issue #771, que este ADR bloquea.

## Decision

### 1. Ruta tecnica: Azure Functions isolated worker + extension MCP (CA-1)

Un servidor MCP del marco es un **Azure Functions isolated worker** mas -- el mismo modelo de programacion que ya usa cada Function App de dominio del BC (MEF-ADR-0020); el plan de hosting queda deslindado en la decision 3 --, construido con la extension oficial `Microsoft.Azure.Functions.Worker.Extensions.Mcp` (paquete NuGet [1]). Esa extension solo soporta el isolated worker model para C# [1], asi que no introduce ninguna decision de runtime nueva frente al resto del marco.

**Transporte y endpoint**: el cliente MCP se conecta por **Streamable HTTP** en `/runtime/webhooks/mcp`. La extension tambien expone Server-Sent Events (SSE) en `/runtime/webhooks/mcp/sse`, pero la documentacion oficial es explicita: *"Newer protocol versions deprecate the Server-Sent Events transport. Unless your client specifically requires it, use the Streamable HTTP transport instead"* [1]. El marco fija Streamable HTTP como transporte por defecto; SSE solo se habilita si un cliente concreto lo exige y no soporta el transporte nuevo.

**Un servidor MCP por Function App**: la configuracion `extensions.mcp` de `host.json` (`instructions`/`serverName`/`serverVersion`) es de alcance de instancia de Function App [1] -- coincide 1:1 con el proyecto `<RootNamespace>.Mcp.{Proposito}` que la decision 2 fija como unidad de granularidad.

**Auth**: por defecto (`system.webhookAuthorizationLevel = "System"`), el endpoint exige la **system key** `mcp_extension`, enviada en el header `x-functions-key` (o el query string `code`); sin ella, el cliente recibe `401 Unauthorized` [1]. Es el mismo mecanismo de credencial-por-Function-App (host key / function key) que cualquier Function HTTP del marco ya usa -- ningun concepto de autenticacion nuevo que aprender.

**Alternativa descartada -- ASP.NET Core + `ModelContextProtocol.AspNetCore`**: Microsoft tambien documenta construir un servidor MCP sobre ASP.NET Core puro, con el SDK oficial de MCP (`builder.Services.AddMcpServer().WithHttpTransport()`, `app.MapMcp(...)`), hospedado en Azure App Service o Azure Container Apps [2][3]. Es una via real y documentada, no una alternativa inventada -- pero introduce un **tercer modelo de hosting** para codigo de un BC que hoy solo conoce dos: Azure Functions isolated worker (todo Function App de dominio, MEF-ADR-0020) y `Microsoft.NET.Sdk.Worker` sin HTTP (el worker de proyecciones, MEF-ADR-0034). Adoptar ASP.NET Core solo para el servidor MCP forzaria replicar, para ese tercer modelo, todo el wiring que el marco ya resolvio para los otros dos -- despliegue por OIDC (MEF-ADR-0022), gate de readiness (MEF-ADR-0031), observabilidad (MEF-ADR-0038) -- sin ganar nada que la extension de Functions no de ya. Adicionalmente, la via self-hosted de servidores MCP construidos con el SDK oficial y desplegados sobre el propio Azure Functions **esta marcada explicitamente como *public preview*** en la documentacion oficial [4], mientras que la extension binding-based (`Microsoft.Azure.Functions.Worker.Extensions.Mcp`) no lleva ninguna advertencia de preview en la documentacion citada [1] -- una senal adicional, no verificada como garantia formal de madurez, mas a favor de la extension que de cualquiera de las dos vias de ASP.NET Core/SDK-hosting.

### 2. Granularidad: un servidor por Bounded Context y por proposito, particion Consultas/Comandos (CA-2)

**Nunca un servidor por dominio.** El marco fija la granularidad de un servidor MCP en el **Bounded Context y el proposito**, nunca en el dominio. La propia especificacion de MCP fundamenta esta granularidad como principio de diseno del protocolo, no como preferencia del marco: *"Servers should be highly composable: each server provides focused functionality in isolation [...] Multiple servers can be combined seamlessly"*, y *"Servers [...] Operate independently with focused responsibilities"* (Model Context Protocol, especificacion 2025-06-18, "Architecture", seccion "Design Principles" y "Core Components" [5]).

La razon de fondo, mas alla de la cita del protocolo: las recetas reales de un asistente conversacional **cruzan dominios**. Una sola pregunta de negocio suele tocar dos o mas dominios del mismo BC a la vez -- tipicamente el dominio que registra el hecho y el que custodia el catalogo contra el que ese hecho se interpreta --; si el servidor MCP fuera uno por dominio, el cliente tendria que orquestar N conexiones y N credenciales distintas para responder esa unica pregunta -- exactamente el costo de composicion que el protocolo busca evitar poniendo la responsabilidad de agrupar en el servidor, no en el cliente. El BC (no el dominio) es la unidad natural: un servidor `<RootNamespace>.Mcp.{Proposito}` agrupa las tools de todos los dominios del BC que ese proposito necesita.

**Particion Consultas/Comandos.** Dentro de un mismo BC, el marco separa las tools de solo lectura de las que mutan estado en **servidores distintos** cuando ambos propositos existen -- tipicamente `<RootNamespace>.Mcp.Consultas` y `<RootNamespace>.Mcp.Comandos`. La motivacion es CQS (Command-Query Separation, Bertrand Meyer, *Object-Oriented Software Construction*, 2.ª ed., Prentice Hall, 1997, cap. 11) llevado a la granularidad de credencial: **el servidor es la credencial de acceso** (la system key `mcp_extension` de la decision 1, unica por Function App). Particionar por Consultas/Comandos es el unico mecanismo de *least privilege* real disponible hoy -- un cliente que solo necesita leer nunca recibe la key del servidor que puede escribir, sin depender de que el propio cliente MCP se autocontenga.

**`ToolAnnotations`/`readOnlyHint` son hints, jamas un mecanismo de seguridad.** MCP permite anotar una tool con metadatos como `readOnlyHint` (¿la tool modifica su entorno?), pero la propia especificacion advierte: *"For trust & safety and security, clients MUST consider tool annotations to be untrusted unless they come from trusted servers"* (Model Context Protocol, especificacion 2025-06-18, "Server Features: Tools", seccion "Data Types: Tool" [6]). Un cliente puede ignorar `readOnlyHint` y ejecutar la tool de todos modos; el hint no impide nada por si solo. La particion en servidores/credenciales distintos de este ADR es la unica frontera de acceso real -- `readOnlyHint` es documentacion util para el modelo, nunca el control de acceso.

### 3. Aislamiento: cliente HTTP puro, contratos propios, tools stateless (CA-3)

**El proyecto MCP no referencia ningun ensamblado del BC.** Ni el `.csproj` de ningun Function App de dominio, ni `PublicEvents`/`PrivateEvents`/`{Dominio}.DomainEvents`/`ReadModels` (MEF-ADR-0039): el servidor MCP es **cliente HTTP puro** (`HttpClient` tipado) contra las Function Apps del BC cuya funcionalidad expone -- exactamente la misma frontera de aislamiento que MEF-ADR-0039 decision 4 ya fija para el worker de proyecciones frente a un Function App, aplicada aqui a un consumidor HTTP en vez de a un lector de event store.

**Contratos upstream redeclarados como isla propia.** El servidor MCP declara su propio DTO/record plano para cada respuesta que consume de una Function App del BC, aunque el Function App de origen ya tenga un tipo equivalente. Es el mismo principio que MEF-ADR-0039 ya fija para los ensamblados de evento -- *"la verdad viaja en el contrato, no en un tipo compartido"* -- aplicado a la frontera HTTP: importar el tipo del BC acoplaria la evolucion del servidor MCP a la evolucion interna del BC, exactamente el riesgo que esa decision ya elimino entre `PublicEvents`, `PrivateEvents` y `{Dominio}.DomainEvents`. El servidor MCP es, en este sentido, una isla mas -- sin `ProjectReference` hacia ningun proyecto del BC.

**Tools stateless.** Ninguna tool mantiene estado de sesion en memoria del servidor entre invocaciones. El motivo no es el plan de hosting sino la naturaleza del host: una instancia de Function App puede reciclarse o escalar horizontalmente en cualquier momento -- en cualquier plan, dedicado incluido --, asi que una invocacion que aterriza en una instancia distinta de la anterior no debe perder nada, porque no habia nada que perder. El contexto conversacional (que se consulto antes, que resultado previo importa) vive enteramente en el **cliente** MCP (Claude, VS Code, u otro host), nunca en el servidor. Es coherente con el propio modelo host-cliente-servidor de MCP: *"Servers should not be able to read the whole conversation, nor 'see into' other servers [...] Full conversation history stays with the host"* (especificacion 2025-06-18, "Architecture", "Design Principles" [5]) -- el servidor nunca tuvo, ni deberia tener, el historial completo que justificaria mantener estado propio.

**Deslinde con MEF-ADR-0020 (plan de hosting).** Este ADR fija el *modelo de programacion* del servidor MCP (Azure Functions isolated worker, decision 1), no su plan de App Service. MEF-ADR-0020 gobierna el plan de un Function App **de dominio**, y proscribe el Consumption `Y1` por una premisa que un servidor MCP de este ADR no carga: el agente de durabilidad de Wolverine (`DurabilityMode.Solo`), con estado en memoria y polling del outbox, que el host puede matar entre invocaciones. Un servidor MCP es cliente HTTP puro y stateless -- sin Wolverine ni outbox --, asi que esa proscripcion no se le extiende automaticamente, y las tools stateless de esta decision dejan abierta cualquier opcion de plan. Elegir el plan concreto (dedicado propio, compartido, o de escalado dinamico) es alcance del issue de scaffold (#768), no de este ADR.

### 4. Diseno de tools: pocas, consolidadas, en lenguaje ubicuo, token-eficientes (CA-4)

**Pocas y consolidadas.** El marco prefiere pocas tools que consoliden varias operaciones internas sobre muchas tools finas y superpuestas. Anthropic documenta la razon con evidencia empirica de agentes reales: *"Too many tools or overlapping tools can also distract agents from pursuing efficient strategies"*, y recomienda que *"Tools can consolidate functionality, handling potentially multiple discrete operations (or API calls) under the hood"* ("Writing effective tools for AI agents", Anthropic Engineering, 2025 [7]).

**Descripciones en lenguaje ubicuo, como atributos.** El nombre y la descripcion de cada tool (`[McpServerTool]`, `[Description]` del SDK/extension) se escriben en el **lenguaje ubicuo** del BC, como constantes de compilacion en el atributo -- no como mensajes runtime. Un modelo de lenguaje decide que tool invocar leyendo esa descripcion antes de la primera llamada; una descripcion tecnica o generica ("obtiene un recurso", "lista entidades") en vez de una escrita con los terminos que el glosario de lenguaje ubicuo del BC ya custodia (MEF-ADR-0040) degrada directamente la capacidad del agente de elegir bien.

**Mensajes runtime en `.resx`.** Los mensajes que una tool produce en **tiempo de ejecucion** -- un error de validacion, un evento de fallo de negocio devuelto como resultado -- siguen la misma doctrina que MEF-ADR-0009 ya fija para aggregates y command handlers: un `.resx` co-localizado con clase `Mensajes` anidada, nunca un string literal inline. La diferencia entre "atributo" (decision de compilacion, lenguaje ubicuo fijo) y "`.resx`" (mensaje runtime, potencialmente localizable) es la misma que MEF-ADR-0009 ya traza entre el nombre de una tool y el contenido de su respuesta.

**Respuestas token-eficientes.** El serializador de respuestas de un servidor MCP usa opciones propias -- `camelCase`, omision de campos `null` (`JsonIgnoreCondition.WhenWritingNull`), y un encoder que no escapa caracteres acentuados (`JavaScriptEncoder.Create(UnicodeRanges.All)` en vez del encoder por defecto de `System.Text.Json`, que escapa como `\uXXXX` todo lo que caiga fuera de Basic Latin) -- en vez de heredar las opciones de serializacion internas del BC (MEF-ADR-0012). Cada caracter acentuado escapado como secuencia `\uXXXX` ocupa mas caracteres que el caracter UTF-8 crudo; en un BC en espanol, con nombres y descripciones llenas de acentos, la diferencia es sistematica, no anecdotica. Anthropic fundamenta la doctrina general detras de esta eleccion: *"We suggest implementing some combination of pagination, range selection, filtering, and/or truncation with sensible default parameter values"* para las respuestas de una tool [7].

**Truncado con senal, nunca silencioso.** Cuando una respuesta se trunca (una lista larga, un resultado extenso), el truncado se declara explicitamente en la propia respuesta -- cuantos elementos hay en total, cuantos se omitieron, como pedir el resto --, nunca un corte silencioso que el modelo no pueda detectar. Anthropic: *"If you choose to truncate responses, be sure to steer agents with helpful instructions"*, y *"Tool truncation and error responses can steer agents towards more token-efficient tool-use behaviors"* [7].

**Filtros que eviten elementos inalcanzables.** Una tool de consulta no devuelve, por defecto, elementos que el agente no puede usar en un paso siguiente (p. ej. entidades en un estado terminal que ninguna tool de comando del BC puede modificar) -- prioriza relevancia contextual sobre exhaustividad. Anthropic: *"Tool implementations should take care to return only high signal information back to agents. They should prioritize contextual relevance over flexibility"* [7].

### 5. Custodia de la key: la genera el host, nunca el consumidor (CA-5)

La system key `mcp_extension` (decision 1) **no se versiona** (nunca en un archivo commiteado), **no se copia como GitHub secret** del repo, y **no se provisiona por Terraform**: la genera automaticamente el host de Azure Functions al desplegar la extension, exactamente igual que cualquier otra function/host key del marco -- ningun modulo Terraform del marco declara ni administra `mcp_extension` como recurso. Es la misma doctrina de custodia de secretos que MEF-ADR-0025 ya fija para el resto del marco (ningun secreto en texto plano; Key Vault o identidad administrada donde aplique), aplicada a una key que ni siquiera requiere ese mecanismo porque el propio runtime la genera y expone via `az functionapp keys list` [1] sin que nadie tenga que crearla ni rotarla a mano.

El **consumo** de esa key en un pipeline de CI (como un smoke test la obtiene, en que secret de GitHub o paso de workflow la usa) es alcance de MEF-ADR-0013/MEF-ADR-0022 extendidos a MCP, y queda fuera de este ADR: se detalla en el ADR de testing dedicado (#767, bloqueado por este ADR).

## Alternativas consideradas

### Alt 1: ASP.NET Core + `ModelContextProtocol.AspNetCore`, hospedado en App Service o Container Apps

Descartada en la decision 1: introduce un tercer modelo de hosting para codigo de un BC (frente a Azure Functions isolated worker y `Microsoft.NET.Sdk.Worker`), obligando a replicar el wiring de despliegue/readiness/observabilidad que el marco ya resolvio para los otros dos, sin ganar nada que la extension de Functions no ofrezca ya.

### Alt 2: servidor MCP autohospedado con el SDK oficial de MCP sobre Azure Functions (`self-hosted MCP server`)

Es una tercera via que Azure Functions documenta explicitamente: hospedar un servidor construido con los SDKs oficiales de MCP (no con la extension binding-based) sobre el propio runtime de Functions. **Descartada por estado de madurez**: la documentacion oficial la marca explicitamente como *public preview* [4], mientras que la extension `Microsoft.Azure.Functions.Worker.Extensions.Mcp` no lleva esa advertencia en la misma fuente [1]. El marco prefiere la via sin advertencia de preview declarada.

### Alt 3: un servidor MCP por dominio

Descartada en la decision 2: fragmentaria contra el principio de composabilidad que la propia especificacion de MCP fija [5], y obligaria al cliente a orquestar multiples conexiones/credenciales para responder una sola pregunta de negocio que cruza dominios del mismo BC -- el caso comun, no la excepcion.

### Alt 4: un solo servidor por BC, sin particion Consultas/Comandos

Descartada en la decision 2: colapsa el unico mecanismo de *least privilege* real que existe hoy para MCP (particionar por credencial de servidor) en una sola credencial que puede tanto leer como escribir. Un cliente que solo necesita consultar terminaria con la misma key que puede ejecutar comandos, y `ToolAnnotations`/`readOnlyHint` no compensan esa perdida porque la propia especificacion los declara metadatos no confiables [6].

### Alt 5: el servidor MCP referencia directamente el codigo del BC (Function Apps o ensamblados de evento)

Descartada en la decision 3, mismo argumento que MEF-ADR-0039 ya aplico al worker de proyecciones: acoplar el servidor MCP a la evolucion interna del BC (tipos, dependencias transitivas de Wolverine/ASP.NET Core/Azure Functions Worker SDK) es exactamente el riesgo que la particion por rol de MEF-ADR-0039 ya elimino para el worker de proyecciones. El cliente HTTP puro preserva la misma independencia de despliegue y de evolucion.

## Consecuencias

### Positivas

- **Ningun BC futuro reinventa estas cinco decisiones desde cero**: ruta tecnica, granularidad, aislamiento, diseno de tools y custodia de la key quedan fijadas como doctrina general, verificable y citada contra fuentes oficiales -- no descubiertas reactivamente bajo presion de un piloto real, como ya paso una vez con la composicion de ensamblados (MEF-ADR-0039).
- **Cero mecanismo de hosting nuevo**: el servidor MCP reusa integramente el modelo de programacion que el marco ya opera para todo Function App (Azure Functions isolated worker) -- mismo pipeline de CI/CD por OIDC (MEF-ADR-0022), mismo artefacto de despliegue -- sin ningun runtime, credencial o mecanismo de auth adicional que aprender. El plan de App Service concreto queda deslindado (decision 3), no heredado a ciegas de MEF-ADR-0020.
- **Least privilege real, no solo declarado**: la particion Consultas/Comandos por servidor/credencial (decision 2) da a un cliente MCP exactamente el acceso que necesita, sin depender de que el propio cliente respete metadatos no confiables como `readOnlyHint`.
- **Aislamiento estructural verificable**: un servidor MCP sin `ProjectReference` hacia ningun proyecto del BC (decision 3) es una condicion que, igual que las de MEF-ADR-0039 seccion 10, se puede afirmar mirando unicamente el `.csproj` -- sin necesidad de inspeccionar logica de negocio.
- **Tools disenadas para uso real de agentes, no solo para exponer una API**: la doctrina de la decision 4 (pocas y consolidadas, token-eficientes, con senal de truncado) reduce el riesgo documentado de que un agente elija mal la tool o desperdicie contexto en respuestas ruidosas.
- **Custodia de la key sin superficie nueva**: `mcp_extension` no exige ningun modulo Terraform ni secreto de GitHub adicional -- la genera el propio host, igual que cualquier otra function key del marco.

### Negativas

- **Dos saltos HTTP en vez de acceso directo**: un servidor MCP que resuelve una consulta hace una llamada HTTP a la Function App del BC, que a su vez consulta Postgres/el read model -- latencia adicional frente a una hipotetica via que referenciara el codigo directamente (Alt 5, descartada). El marco acepta ese costo a cambio del aislamiento de la decision 3.
- **Duplicacion deliberada de contratos**: cada DTO que el servidor MCP consume de una Function App del BC se redeclara como tipo propio (decision 3) -- mas superficie de mantenimiento cuando el contrato upstream cambia, mismo trade-off que MEF-ADR-0039 ya acepto para los ensamblados de evento.
- **Mas Function Apps por BC**: cada proposito nuevo (Consultas, Comandos, u otro) que amerite particion suma un `<RootNamespace>.Mcp.{Proposito}` mas -- mas proyectos .NET, mas pipelines de deploy, mas keys que administrar (aunque cada una la genera el host sin trabajo manual).
- **La particion Consultas/Comandos exige que alguien la evalue por BC**: a diferencia de un default unico (siempre un servidor por BC), este ADR pide que el consumidor decida, al disenar el servidor, si el proposito amerita separar lectura de escritura -- trabajo de analisis que un default incondicional no exigiria.
- **El ADR no resuelve testing ni scaffold**: hasta que #767/#768/#769/#770/#771 se implementen, un consumidor que adopte esta doctrina hoy la aplica manualmente, sin agente scaffolder ni ADR de CI dedicado.

- Bertrand Meyer, *Object-Oriented Software Construction*, 2.ª ed. (Prentice Hall, 1997), cap. 11 -- Command-Query Separation (CQS): fundamento de la particion Consultas/Comandos de la decision 2, llevada aqui a granularidad de credencial de acceso.
- MEF-ADR-0009 (patron de mensajes `.resx` per-aggregate): la decision 4 extiende esta doctrina a los mensajes runtime de una tool MCP, distinguiendolos de la descripcion de la tool (constante de compilacion en lenguaje ubicuo).
- MEF-ADR-0012 (encapsulamiento, frontera de serializacion event store vs bus): la decision 4 diverge deliberadamente de sus opciones de serializacion internas para las respuestas de un servidor MCP (token-eficiencia como criterio distinto de la frontera event store/bus).
- MEF-ADR-0013 (smoke tests contra entorno dev) y MEF-ADR-0022 (autenticacion de CI por OIDC): hermanos citados en "Aplica a"; su extension a servidores MCP (como probarlos en CI, con que credencial) es alcance del issue #767, que este ADR bloquea sin resolverlo.
- MEF-ADR-0020 (hosting de Azure Functions, un App Service Plan por dominio): fuente del modelo de programacion (Azure Functions isolated worker) que la decision 1 reusa para el servidor MCP; su proscripcion del plan Consumption `Y1` no se extiende al servidor MCP, por el deslinde explicito de la decision 3.
- MEF-ADR-0040 (fuentes de conocimiento del dominio): el glosario de lenguaje ubicuo que el `planner` custodia es la fuente del vocabulario con el que la decision 4 exige escribir el nombre y la descripcion de cada tool.
- MEF-ADR-0025 (custodia de secretos): fuente de la doctrina general de custodia que la decision 5 aplica a la key `mcp_extension`, notando que ni siquiera requiere Key Vault porque el host la genera y expone directamente.
- MEF-ADR-0034 (worker de proyecciones y read models por Bounded Context): fuente del segundo modelo de computo (`Microsoft.NET.Sdk.Worker`) que la decision 1 cita como precedente de que el marco ya sostiene mas de un modelo de hosting, y que ASP.NET Core (Alt 1) habria sumado como un tercero.
- MEF-ADR-0030 (esquema de identificacion de ADRs): fija el numero `MEF-ADR-0047` (numero verificado libre, `docs/adr/` llegaba a 0046 antes de este ADR).
- MEF-ADR-0039 (composicion canonica de ensamblados por rol del evento): fuente directa del principio "la verdad viaja en el contrato, no en un tipo compartido" que la decision 3 aplica al servidor MCP, y de la prohibicion analoga (el worker nunca referencia un Function App, seccion 10 de ese ADR) que inspira la prohibicion equivalente de esta decision.
- Issue #761 de este repo (origen de este ADR): registra la evidencia empirica del piloto que valido esta doctrina -- que consumidor, que issues y PRs, que resultado de smoke --, deliberadamente fuera del cuerpo del ADR (ver "Alcance").
