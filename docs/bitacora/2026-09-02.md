# 2026-09-02 - Reconstruir sin el repo de referencia: cinco desviaciones del mismo path del PRM

> Dos drafts nacidos un día después de que 0.35.0 empaquetara la doctrina MCP completa revelaron que reconstruir el módulo `apim-mcp-api` solo con la especificación escrita, sin el repo del pionero a la vista, regresionaba cuatro trampas ya pagadas -- y a mitad de la sesión el pionero aplicó su propio fix del path del PRM en caliente, sumando una quinta desviación que obligó a partir en tres lo que había empezado como un solo issue.

## Lo que se logró

- **#826 resuelto en la misma sesión**: el skill `/scaffold-mcp` informaba el alcance de 0.34.0 aunque el agente ya generaba identidad/OAuth app-side desde #819 -- deriva estructural entre la prosa del skill (bloque "1. Informar que se va a generar") y la lista real de artefactos del agente. Se alinearon ambas listas y se sumó impresión de la versión del plugin (`.claude/pipeline/.plugin-root` + `jq -r .version`), acotado solo a `/scaffold-mcp` (PR #828).
- **#827 (regresiones de `apim-mcp-api`) diagnosticado contra el clon local del pionero** (`../Bitakora.ControlAsistencia`): cuatro desviaciones invisibles para `validate`/`plan` -- orden de hijos de `validate-jwt` (verificado en Microsoft Learn: `openid-config -> issuer-signing-keys -> decryption-keys -> audiences -> issuers -> required-claims`; el error fue extrapolar el orden de login a la variante MCP/Connect), hostname regionalizado, concatenación del sufijo del wildcard, y la forma real de `azapi_resource_action` para `listkeys` (`Microsoft.Web/sites/host@2023-12-01` + `action = "listkeys"`, distinta de la verificada solo contra el registry). Primera pasada: se mantuvo como un solo issue (PR #836 reconcilia el módulo con el HCL verificado del pionero).
- **A mitad de la sesión, el pionero aplicó su propio fix del path del PRM** (#575, PR #579 del consumidor): el primer apply falló en rojo creando la API PRM compartida con `path = ".well-known/oauth-protected-resource"` (`400 ValidationError` sin campo, APIM rechaza un path con punto inicial -- regla server-side no documentada) y se corrigió con hotfix `a54ac6b` (path sin punto, re-apply verde). Esa evidencia llegó como "quinta desviación" a #827 y obligó a **revertir la decisión de "un solo issue"**: con cinco desviaciones mezclando dos causas raíz (reconstrucción sin repo de referencia vs. regla server-side de APIM), la quinta desviación se separó del resto en dos issues nuevos. #831 corrige el path sin punto con la regla documentada, deriva `prm_url` de la API compartida por variable en vez de hardcodearlo, y cierra el caveat "NO VERIFICADO" con los dos runs de evidencia (PR #837); #833 alinea la prosa de `mcp-scaffolder` que aún afirmaba la ubicación con punto (PR #839).
- **#832 (draft ADR) enmienda MEF-ADR-0032 sección 9**: fija la ubicación del PRM fuera del well-known de RFC 9728 por la restricción de APIM, y registra que el descubrimiento se garantiza **exclusivamente** por el `resource_metadata` del header `WWW-Authenticate` (RFC 9728 sección 5.1) -- no por convención. Durante el refinamiento se descubrió que la sección 9 tenía texto **obsoleto**, no solo incompleto: describía el PRM como "una operación de la misma API" cuando desde #820 vive en la API compartida `mcp-prm` al nivel del host -- la enmienda dejó de ser puramente aditiva (regla del marco: nunca marcar "obsoleto" en el cuerpo, solo el control de cambios lo registra) (PR #838).
- Los cinco issues del día cerraron y mergearon: #826 (PR #828), #827 (PR #836), #831 (PR #837), #832 (PR #838), #833 (PR #839).

## Problemas encontrados

1. **Reconstruir HCL sin el repo de referencia sale caro**: las cuatro regresiones originales de #827 son invisibles para `validate`/`plan` -- el pionero ya las tenía documentadas en comentarios de su `infra-reviewer`, y con el clon local disponible el diff tomó minutos en vez de descubrirlas una por una en producción.
2. **APIM rechaza un `path` con punto inicial en `azurerm_api_management_api`**: regla server-side no documentada -- la doc REST de Api Create Or Update solo declara min/maxLength para `properties.path`. Invisible para `validate`/`plan`, igual que las otras cuatro; solo un apply real la reveló.
3. **Un apply que destruye la API PRM vieja y falla al crear la nueva deja el 401 apuntando a un 404** durante el intervalo: las reconexiones OAuth caen ahí (las sesiones con token vigente siguen, `validate-jwt` no cambia). Aplica a cualquier cambio futuro del path del PRM compartido -- quedó anotado como advertencia en el checklist post-deploy de #831.

## Lo que descartamos

- **Absorber la quinta desviación (path sin punto) dentro de #827**: decidido así en la primera pasada, revertido al llegar la evidencia real del apply del pionero -- mezclaba dos causas raíz distintas en un solo issue de ~11 CAs.
- **Hardcodear el segmento del PRM en `local.prm_url`** como hace el pionero: se prefirió una variable derivada de la API compartida (`mcp_prm_api_path = azurerm_api_management_api.mcp_prm.path`) para que `prm_url` coincida por construcción.
- **Que #832 dependa de #831 o viceversa**: el ADR documenta una decisión ya aplicada en el consumidor; el orden no importa técnicamente.
- **Adoptar del pionero su PRM como API propia por servidor, `prm_path`, `resource_audience` ni `protocol_methods`**: Mefisto conserva el PRM compartido por servidor (RFC 9728 sección 3.1) y los outputs `resource_uri`/`prm_url`.
- **Un guard automático de deriva skill<->agente** en `test-guards.sh`: descartado -- es prosa contra prosa, no una comparación estructural barata.
- **Issue transversal de "imprimir versión del plugin" en todos los scaffolders**: acotado solo a `/scaffold-mcp`.

## Aprendizajes

1. **Reconstruir infraestructura HCL desde una especificación escrita, sin la implementación de referencia que ya sobrevivió a un apply real, reintroduce exactamente las trampas que esa referencia ya pagó** -- un diff contra el clon local es un seguro barato frente a redescubrirlas en producción.
2. **Una decisión de arquitectura puede verse puramente aditiva en el papel y resultar en prosa obsoleta que hay que reescribir, no solo completar**, una vez se verifica contra el estado realmente aplicado -- siempre verificar contra lo que vive, no solo contra lo que el ADR decía la última vez.
3. **Mantener un hallazgo como un solo issue no es un compromiso permanente**: cuando la evidencia nueva cambia la cuenta de CAs y mezcla causas raíz distintas, partirlo es la corrección correcta, incluso a mitad de refinamiento.
4. **Las reglas de validación server-side no documentadas en la API REST del proveedor (como el path con punto inicial de APIM) solo se revelan con un apply real fallido** -- el silencio de la documentación no es tranquilidad, es una señal de alerta.
