# 2026-07-26 - El read-side completo en un día, y el gate que no podía aprobarse a sí mismo

## Problemas encontrados

Tres incidentes, todos fallos estructurales del propio harness -- no del código de dominio -- y los tres dejaron issues de seguimiento.

1. **El writer creó su propio PR (issue #360 → PR #376), y el batch siguió sin mergearlo.** En el batch paralelo de oleada 0 (`mefisto-batch-125628`), a las 13:03:36 el agente `writer` del issue #360 hizo push y abrió él mismo el PR #376 -- su log terminó con "El PR quedó creado". A las 13:15:08, el pipeline intentó `gh pr create` para el mismo issue y GitHub lo rechazó por duplicado (`a pull request for branch [...] already exists`). El pipeline marcó #360 como failed y **continuó con #361 sin mergear #360 primero**, rompiendo el invariante "cada eslabón corre sobre el merge del anterior". Consecuencia: cuando #361 mergeó primero (PR #377, 13:36), el PR #376 de #360 quedó **CONFLICTING** contra `main` -- conflicto de adyacencia en `CHANGELOG.md` y `CLAUDE.md`, los dos archivos-índice que cualquier ADR nuevo toca -- y hubo que resolverlo a mano (`merge: integrar origin/main` a las 13:41:22). Al resolver el conflicto se descubrió que el PR #377 tampoco había actualizado el conteo de ADRs del `README`. De ahí salieron tres issues de seguimiento -- **#378** (prohibir al writer crear PRs y reutilizar el existente, → PR #381, 14:24 local), **#379** (propagar la causa real del fallo externo en los mensajes de abort -- el log del batch solo mostraba "No se pudo crear el PR" genérico, había que abrir un segundo archivo de log para ver el motivo real, → PR #382, 14:43 local) -- y un cuarto issue hermano, **#396** (quitar la tabla de agentes de `CLAUDE.md` y las cifras de inventario del `README`, creado más tarde ese mismo día → PR #400, 21:26 local), nacido de la misma causa raíz (contenido derivable mantenido a mano que se desincroniza con cada ADR/agente/skill nuevo).
2. **#380 falló DOS veces por bloqueo auto-referencial -- el incidente más interesante del día.** #380 introduce el mecanismo de fragmentos `changelog.d/` para eliminar la contención de raíz del incidente 1. Pero `.claude/scripts/mefisto-tooling-pipeline.sh:17` carga `_mefisto-common.sh` desde su **propia** ubicación y el pipeline corre siempre desde `main`, así que los gates evalúan el worktree contra la versión de main -- la de *antes* del cambio. Primer intento: rechazado por `is_path_in_mefisto_scope` porque `changelog.d/` no estaba en la allowlist que el propio PR quería crear. Segundo intento (tras desbloquear el primero): rechazado por `check_unreleased_touched` porque el writer, correctamente, había anotado su cambio como fragmento en vez de editar `CHANGELOG.md` -- exactamente lo que su propia definición de hecho pedía, y el gate viejo lo rechazó por no encontrar una entrada monolítica. **Esto no es un bug a corregir**: que el gate se cargue desde `main` es una propiedad de seguridad -- si leyera la copia del worktree, cualquier writer podría añadirse un `*) return 0 ;;` y escapar del scope. El remedio es de secuencia, no de código, y es el mismo patrón de dos pasos que ya funcionó con `skills/` (#360 registró la ruta sin usarla, #364 la usó después con la ruta ya en `main`). Se desbloqueó con dos PRs manuales previos: **#399** (registra `changelog.d/*` en la allowlist de scope, sin crear ningún fragmento bajo ella, 20:51 local) y **#401** (hace `check_unreleased_touched` tolerante: acepta fragmento *o* entrada monolítica como alternativa transitoria -- el gate estricto de solo-fragmentos lo instala el propio #380 al aterrizar, 21:45 local). #380 finalmente mergeó como PR #403 a las 22:15 local. Ambos PRs de desbloqueo dejaron anotado, "fuera de alcance", que MEF-ADR-0019 debería documentar explícitamente la regla "registrar/reemplazar un gate va en un PR previo al que lo usa" -- hoy es conocimiento tribal redescubierto cada vez.
3. **El release no pudo crear su propio PR.** `mefisto-release.sh` vuelca el CHANGELOG completo de la versión en el cuerpo del PR; la sección `[0.18.0]` mide **109.010 caracteres** (27 entradas, algunas de más de 5.000 caracteres cada una) -- 1,66x el límite duro de 65.536 de la API de GitHub (`GraphQL: Body is too long`). Todo lo demás de la fase *prepare* (rama, consolidación de fragmentos, reescritura del CHANGELOG, bump de `plugin.json`, commit, push) se completó bien; solo abortó la llamada final a `gh pr create`, y el PR #404 se creó a mano. Quedó abierto el issue **#405** (creado la madrugada siguiente, ya `estado:listo`) para acotar el cuerpo del PR de release en vez de incrustar las notas completas.

## Lo que descartamos

- **Bolt-on de la doctrina read-side a `test-writer`/`implementer`**: descartado -- infla el 80% del contrato que ya sirve al write-side. Se prefirió un Skill (`projections`) + dos subagentes dedicados.
- **Un `projection-pipeline.sh` dedicado**: descartado -- se reusa `tdd-pipeline.sh` con una rama read-side que dispatcha a los subagentes correctos por label, evitando duplicar la orquestación de stages.
- **Estandarizar ahora las recetas Event Projection / Custom (N3)**: diferido -- Async/Inline y SingleStream/MultiStream (N1/N2) cubren el caso común; N3 queda como escape hatch justificado, no como estándar (Rule of Three, MEF-ADR-0018).
- **Calcar el naming y las decisiones de `Cosmos.ControlPlane`**: descartado en varios puntos -- read models mutables (aquí inmutables/records), `Query().FirstOrDefault` (aquí `LoadAsync`), `XQueriesEndpoint` agrupado (aquí carpeta por query). ControlPlane fue la fuente de vocabulario, no la especificación final.
- **Tema 2 de la sesión de planning (CorrelationId/CausationId + `TraceContextMiddleware`)**: **parqueado** por decisión explícita del usuario -- todavía experimental de su lado como para fijarlo en el harness. No se creó issue ni ADR; retomar empezando por dónde vive el middleware (nuget building block vs. generado por Mefisto).
- **Opción A del incidente de changelog (re-sincronizar con `main` en la ventana entre sync y merge)**: descartada -- solo reubica el conflicto sin eliminar la causa raíz, dejando que un LLM lo resuelva sobre archivos-índice compartidos sin supervisión humana, que es exactamente el modo de fallo del incidente 1. Se prefirió el mecanismo de fragmentos, que elimina la contención de raíz (dos PRs nunca tocan el mismo archivo).

## Aprendizajes

1. **Un backlog grande no es un problema si el grafo de dependencias está bien trazado.** Los 16 issues de esta sesión de planning se organizaron en 4 oleadas explícitas (#364←#360,#362,#363; #375←#367; #372←#371; etc.) y corrieron con `/parallel`/`/sequential` sin bloqueos reales -- el único fallo de coordinación (incidente 1) no fue del grafo sino de un writer saliéndose de su contrato.
2. **Cuando un agente se sale de su contrato, el batch debe abortar la cadena entera, no solo marcar el issue como failed y seguir adelante.** Continuar con #361 sin mergear #360 primero fue lo que convirtió un error de un solo PR en un conflicto de merge que costó resolver a mano.
3. **Un pipeline que se carga desde `main` por diseño, y no desde el worktree, es una propiedad de seguridad -- no un bug a "corregir".** La consecuencia inevitable es que ningún PR puede reemplazar un gate y pasar ese mismo gate en el mismo PR; el remedio es siempre de secuencia (un PR previo que solo registra, luego el PR que usa lo registrado), nunca de relajar la carga del gate.
4. **Ese patrón de dos pasos debería ser una regla explícita del ADR de gobierno (MEF-ADR-0019), no conocimiento tribal redescubierto cada vez que un artefacto nuevo choca contra el gate.** Ya van dos casos reales (`skills/` con #360/#364, `changelog.d/` con #399/#401) resolviéndose con el mismo patrón sin que esté escrito en ningún lado todavía.
5. **Ningún límite de una API externa es "demasiado improbable de tocar" cuando el contenido crece con el proyecto.** El CHANGELOG de este repo genera entradas de varios miles de caracteres cada una; volcar la sección completa en el cuerpo de un PR de release iba a reventar el límite de GitHub tarde o temprano, y lo hizo en el primer release después de resolver la contención de fragmentos -- una validación real de que el rediseño de #380 funciona, incluso mientras exponía un problema distinto.
6. **El primer uso en producción de un mecanismo nuevo es la única verificación que cuenta.** La consolidación de fragmentos de #380 se comprobó a mano contra el release real: los fragmentos correctos se consumieron y borraron, el README del mecanismo correctamente no se tocó, y `[Unreleased]` quedó vacío -- ninguna cantidad de tests unitarios reemplaza correr el camino completo una vez.
