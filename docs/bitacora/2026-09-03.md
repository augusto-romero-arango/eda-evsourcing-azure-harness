# 2026-09-03 - El middleware que restaura lo que la extensión MCP coerciona

> Un bug del consumidor -- toda fecha válida rechazada por `registrar_colaborador`/`listar_colaboradores` -- llevó a verificar la causa raíz directo en el `main` de la extensión MCP de Azure Functions Worker, y a descubrir que el fix del consumidor no fue el helper por-tool que proponía el draft original sino un middleware que intercepta los argumentos crudos antes de que el host los coeccione.

## Lo que se logró

- **Causa raíz verificada en el upstream de `Microsoft.Azure.Functions.Worker.Extensions.Mcp` 1.6.0**: `DictionaryStringObjectJsonConverter.ReadString` (`TryGetDateTimeOffset` + `Guid.TryParse`) y `McpInputConversionHelper` (fallback `Convert.ToString(InvariantCulture)` con destino `string`) convierten `"2026-09-01"` en `DateTimeOffset` y lo re-serializan como `"09/01/2026 00:00:00 +00:00"` cuando el parámetro declarado es `string`. El issue upstream #129 se cerró "completed" el 2025-11-25, pero el fix solo reemplazó el `null` por ese `ToString` -- no preserva el texto original (pregunta sin respuesta desde 2025-11-26). Se decidió no abrir issue upstream (decisión del experto).
- **El consumidor no adoptó el helper por-tool que sugería el draft: usó un middleware** (`ArgumentosCrudosMcpMiddleware`, `IFunctionsWorkerMiddleware`) que lee el JSON crudo de `context.BindingContext.BindingData[<trigger>]` -- donde el host deja los argumentos verbatim -- y reemplaza `context.Items["ToolInvocationContext"]` por una copia con las hojas `string` restauradas. Recupera fecha **y** GUID (el helper no podía recuperar casing/formato de un GUID), sin tocar firmas ni `inputSchema`, fail-open si upstream cambia sus internals. Se verificó que **el orden de middlewares importa**: debe ir después de `ConfigureFunctionsWebApplication()` y antes de cualquier middleware que haga `BindInputAsync<ToolInvocationContext>` (ese bind cachea en `IBindingCache` bajo el nombre del parámetro, y la tool recibiría el diccionario ya coercionado) -- hallazgo del reviewer del PR #591 del consumidor, verificado por decompilación de `Microsoft.Azure.Functions.Worker.Core` 2.52.0.
- **Desglose en cuatro issues, ADR primero y agentes después** (revirtiendo el "fundir en uno" de #789 la semana anterior, porque esta vez los agentes necesitaban citar doctrina ya escrita): #840 (`agents/mcp-scaffolder.md` genera siempre `Infraestructura/ArgumentosCrudosMcpMiddleware.cs`, lo cablea como primer middleware propio en ambas variantes de `Program.cs` con comentario de posición, y suma unit tests del núcleo -- `ToolInvocationContext` es `public class` con propiedades `init`, testeable sin `FunctionContext`), #841 (enmienda MEF-ADR-0047 con la restricción conocida de la extensión + MEF-ADR-0048 exigiendo que la tool call real ejercite con valor válido cada parámetro fecha/identificador -- el error path no la sustituye), #842 (la tool de ejemplo `ejemplo_listar` gana el parámetro opcional `fecha_referencia` con validación `yyyy-MM-dd` y smoke del camino válido con eco exacto, para que un scaffold fresco detecte en su primer deploy si el middleware quedó fail-open), #843 (operacionaliza la exigencia en `smoke-test-writer`, `reviewer` y `planner`, mismo patrón que #789). Los cuatro cerraron y mergearon la misma tarde (PR #845, #846, #847, #848).
- **Evidencia de éxito del lado del consumidor**: PR #591 mergeado 2026-09-03 12:52; `Deploy MCP Comandos`/`Deploy MCP Consultas` (con el job de smoke encadenado) en verde sobre `ad802d8`; unit tests 48/48 y 82/82.

## Problemas encontrados

1. **El smoke del propio scaffold tenía exactamente la forma que dejó pasar el bug**: la tool de ejemplo (`ejemplo_listar`) solo ejercitaba una tool call sin parámetros más el error path del `.resx` -- ningún parámetro fecha/identificador, así que un scaffold fresco nunca podía haber detectado esta clase de bug por sí mismo.
2. **El "fix completo" de upstream no lo era**: el issue #129 cerró como "completed" hace meses, pero solo cambió un `null` por un `ToString` con pérdida -- el texto original de la fecha sigue sin preservarse. Confiar en el estado "completed" del tracker upstream sin leer el diff real habría dejado pasar el mismo bug.
3. **Gap lateral detectado pero no cerrado**: el gate de cobertura (clasificación MCP del issue #788) deja `Infraestructura/*Middleware.cs` como "sin clasificar" -- solo reconoce `*Api.cs`. Queda como draft pendiente de crear.

## Lo que descartamos

- **Helper por-tool sobre `context.Arguments`** (la propuesta original del draft, el mismo workaround sugerido en upstream #129): no recupera casing/formato de GUID, acepta variantes que la tool no promete, y obliga a tocar cada tool y cada parámetro futuro uno por uno.
- **Parámetro `DateTimeOffset`**: un valor inválido pasaría a error de protocolo, contra MEF-ADR-0047 decisión 4.
- **Parámetro `object`**: rompe el contrato `type: string` del `inputSchema`.
- **Bajar la versión del paquete**: la coerción existe desde `1.0.0-preview.7`, no es regresión de la 1.6.0.
- **Fundir #841 y #843 en un solo issue** (como hizo #789 la semana pasada): se prefirió ADR primero, agentes después, para que estos últimos citen doctrina ya escrita en vez de manejarla implícita.

## Aprendizajes

1. **Un workaround estructural (middleware que intercepta el binding data crudo) puede recuperar más fidelidad que un helper puntual por-tool** (casing y formato de GUID, no solo el valor), al costo de exigir documentación cuidadosa del orden de middlewares.
2. **Verificar la causa raíz directo en el código fuente upstream, no solo confiar en el estado "completed" de un issue tracker, revela cuándo un fix declarado completo sigue siendo incompleto** para el caso propio.
3. **El smoke de ejemplo de un scaffold necesita ejercitar cada tipo de parámetro que dice soportar** (fechas, identificadores) o no puede autodetectar regresiones en el patrón exacto que se supone debe cubrir.
4. **Fundir o separar issues de doctrina relacionados no es una regla fija**: depende de si los issues posteriores necesitan citar doctrina que uno anterior todavía no ha escrito.
