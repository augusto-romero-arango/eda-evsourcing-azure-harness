- `projections-scaffolder` gana un paso nuevo (Paso 1d, entre el config-test base y el Dockerfile) que crea `Infraestructura/ConfiguracionObservabilidadProjections.cs`, el seam hermano de `ConfiguracionMartenProjections` (MEF-ADR-0029) que cierra el cable de observabilidad que el harness ya paga (`infra-base-scaffolder` inyecta `APPLICATIONINSIGHTS_CONNECTION_STRING` en el Container App) pero que hasta ahora nadie consumia del lado del codigo. El worker de proyecciones no tiene `UseFunctionsWorkerDefaults()` (no es una Function App), asi que nada fija su `service.name` por convencion como en el write-side; sin este seam, OpenTelemetry cae al default `unknown_service:dotnet` -- defecto ya medido en produccion por el consumidor Bitakora.ControlAsistencia (issues #250/#263) tras copiar el seam del write-side tal cual. El seam configura `AddOpenTelemetry().ConfigureResource(r => r.AddService(Assembly.GetExecutingAssembly().GetName().Name!))` (resuelve a `<RootNamespace>.Projections` sin sustitucion de token del agente, y ata el `service.name` al nombre de la `ActivitySource` propia por construccion), `WithTracing` con las fuentes `Marten`, `Npgsql` (asimetria deliberada frente al write-side: el daemon poolea Postgres de forma sostenida y esas dependencias son la senal principal de su salud) y la propia del ensamblado con el patron sin punto delante del `*` que valida el issue #460, y `.UseAzureMonitorExporter()` -- el seam no lee ni recibe la connection string, que el exporter resuelve del entorno por convencion propia (MEF-ADR-0025). El `.csproj` del worker suma exactamente dos paquetes nuevos, `OpenTelemetry.Extensions.Hosting` 1.17.0 y `Azure.Monitor.OpenTelemetry.Exporter` 1.8.3 (verificados contra NuGet.org, pin independiente del trio write-side de MEF-ADR-0003), con un comentario que descarta `Microsoft.Azure.Functions.Worker.OpenTelemetry` (el worker no es Functions) y `Azure.Monitor.OpenTelemetry.AspNetCore` (el worker no es ASP.NET Core y no recibe requests). `Program.cs` invoca el seam nuevo encadenado antes de `ConfigurarEventos`, sin wirear OpenTelemetry inline (MEF-ADR-0029). El seam deliberadamente no instala ningun `Sampler`: el worker corre 24/7 (`min_replicas >= 1`) a diferencia de las Function Apps que escalan a demanda, y el punto de extension queda documentado (`ParentBasedSampler(new TraceIdRatioBasedSampler(ratio))`) para que el ratio siga siendo politica de costos del consumidor, nunca doctrina del marco. Idempotente con su propio probe de existencia (estilo Pasos 1b/1c): nunca sobrescribe el seam si ya existe, y corre siempre -- incluso sobre un worker scaffoldeado con una version de este agente anterior a este issue.
