- El bloque `paths` del trigger `push` de `deploy-{kebab}.yml`, generado por `domain-scaffolder` (Paso 5), no cubria sus propias dependencias de build: faltaban `global.json` y el propio archivo del workflow. `global.json` es un input real del build aunque `actions/setup-dotnet` no lo lea (recibe `dotnet-version` explicito, y su input `global-json-file` no se usa): lo leen el muxer del CLI y el resolver de SDK de MSBuild al correr `dotnet restore`/`dotnet build`, asi que su `version` (piso) y su `rollForward` (politica) deciden con cual de los SDK instalados se compila el dominio. El modo de fallo no era una rotura -- el CI del PR la atrapa antes del merge -- sino staleness silenciosa: la Function App queda sirviendo un binario construido con el SDK anterior, sin aviso. Verificado en el consumidor `Bitakora.ControlAsistencia`, donde `deploy-projections.yml` (escrito a mano espejando esta plantilla) heredo el defecto y ninguno de los dos cambios que lo afectaban (PR #257, que creo el propio workflow, y PR #258, que arreglo `global.json`) lo disparo -- hubo que lanzar `workflow_dispatch` a mano las dos veces. Se agregan las dos rutas al filtro (`'global.json'` y `'.github/workflows/deploy-{kebab}.yml'`), con un comentario junto al bloque que documenta ademas las dos exclusiones deliberadas, para que nadie las agregue despues buscando simetria: `<SolutionFile>` (un cambio al `.slnx` por este dominio ya viene acompanado de cambios en `src/<RootNamespace>.{PascalCase}/**`, que disparan igual, y por otro dominio no altera el binario de este) e `infra/**` (su trigger vive en `infra-cd.yml` y este workflow se encadena detras via `workflow_run` para preservar el orden infra -> deploy, MEF-ADR-0022 / issue #197). El agente gana ademas una nota de mantenimiento con las fuentes de ese mecanismo y la advertencia de copiar el filtro completo al generar otro workflow de deploy a partir de esta plantilla -- copiarla sin las dos rutas es exactamente como el defecto llego al consumidor.
