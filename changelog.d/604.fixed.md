- Se cierra la carrera entre el smoke de un Function App ajeno y su deploy concurrente (MEF-ADR-0031 seccion 4 enmendada): el fallback a "solo 200" del readiness gate por SHA no es seguro cuando un `deploy-{kebab}.yml` de otro dominio sigue tocando el FA bajo prueba en el mismo commit -- diagnosticado en el consumidor `Bitakora.ControlAsistencia` (`Deploy Projections` en rojo desde 2026-08-07, 4 de 4 solapamientos con `Deploy ControlHoras`). La plantilla `smoke-tests-dominio.yml` (`agents/domain-scaffolder.md`, Paso 6.1) gana un paso previo al warmup, condicionado a `inputs.expected_sha == ''`, que espera el **job** `deploy` (nunca el run completo, para no deadlockear contra el `concurrency` que ese run ajeno ya tiene tomado) de cualquier run del mismo commit cuyo workflow empiece con `Deploy `; falla explicitamente si un run ajeno no expone ese job en vez de degradar en silencio. Requiere `actions: read` en el job que hace `uses:` de los invocadores (`deploy-{kebab}.yml` Paso 5, `smoke-tests.yml` Paso 6.2) y en el propio reutilizable -- sin esa concesion el run muere en `startup_failure` sin annotation visible. El filtro de runs excluye por `path` el `deploy-projections.yml` del worker de proyecciones (`projections-scaffolder`): comparte el prefijo `Deploy ` pero publica un Container App, no toca ninguna Function App y sus jobs son `build-and-test`/`publish`, asi que sin la exclusion la guarda abortaria contra un run que nunca tuvo nada que esperar. El bloque `[H]` de `scripts/tests/test-guards.sh` afirma la correspondencia entre los literales de la guarda y las plantillas de los dos agentes. Documenta el parche manual para repos ya scaffoldeados, cuya idempotencia impide regenerar estos tres archivos.
